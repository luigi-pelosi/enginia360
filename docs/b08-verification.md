# B08 — Explicit partial installation and stock consumption

## Scope, decision and ownership

D72 records the owner's confirmed explicit installation of 1 of 2 picked: consume 1, physical −1, leave 1 picked/not installed. D70 authorizes sequential synthetic/ephemeral delivery, not a new persistent/manual environment or public deployment. Baseline B07 PR #28/main `fcc62ca8aefbca4e7bf66e413f063d97f85bf9df`.

Workshop owns the immutable technical installation. Inventory owns the immutable consumption and physical balance. They communicate through public immutable contracts only, without querying each other's tables or sharing a transaction. The bounded existing job/working-group ID remains the order ID. Installation retains order/job/line, pick/reservation, verified tenant/company/header site/warehouse, catalog identity/version, source document type/configuration version, picking configuration version, operator and server UTC timestamp normalized to PostgreSQL microseconds. The source configuration reference is provenance, not a universal freeze of future company customizing. No handover, carcass receipt, release/cancellation, unused-new return, cost, valuation or fiscal effect is fabricated.

## Contract and balances

`GET/POST /api/v1/workshop/orders/{orderId}/lines/{lineId}/picks/{pickId}/installations` uses verified membership and exact source provenance. POST accepts only nonempty `id` and explicit positive invariant `quantity` string, maximum six decimals and technical bound `999999.999999`. Unknown/server-owned fields, signs, exponents, nonfinite values, overflow and uncovered quantities fail without trimming, rounding, completion or whole-order block.

- Workshop command identity lock → pick cumulative lock → fresh local installed sum → immutable technical insert/commit. Quantity cannot exceed picked minus already installed (including installations whose consumption is pending).
- After that commit, Inventory reads the technical fact through its public contract, reauthorizes, locks consumption identity and the same stock row used by reservation, and atomically inserts consumption plus physical decrement. No cross-module transaction is claimed.
- Reservation/picking quantities remain immutable historical facts and continue to bound lifetime line/pick capacity. Active stock commitment = original reservation quantities minus committed consumption quantities. Availability = physical minus active commitment. Consuming already committed stock reduces physical and commitment equally, neither double-counting the original reservation nor freeing stock for another order.
- Identical retries return original persisted identities/quantities/timestamps; changed quantity/pick and another tenant's globally colliding command ID return controlled conflict. Each effect is applied once.
- A stock failure after technical commit returns HTTP 202 with installation and `stockEffect: Pending`; Inventory transaction rolls back both consumption and physical update. GET shows the pending fact. Repeat the same command (or use **Recupera consumo**) to recover after a restart, without deleting/recreating the technical installation. No automatic worker, distributed atomicity or exactly-once transport promise is added.

Read/create are independent `workshop.installations.*` and `inventory.consumptions.*` actions, combined with Workshop order read, verified company/header site/warehouse and existing capability checks. Disabled capability prevents writes while preserving authorized historical reads. Inventory releases lookup connections before access/Workshop calls; Workshop releases its transaction before Inventory calls, including shared pool size one. Forced tenant RLS, non-bypass application role and insert-only fact grants supplement resource authorization. Installation routes are absent when Inventory is disabled.

The current application expects the full migration, even when only exercising older reservation/picking behavior. It restores fixture stock from committed consumption and removes both B08 fact tables while preserving earlier order/line/pick/reservation facts. It is not a valid compensation of real installed parts. Operational rollback: disable new Inventory/installation writes, retain schema/facts, snapshot/export and redeploy the previous approved image; assess balances rather than erasing technical reality. Any real data-loss or compensation policy requires separate approval. No persistent environment is deployed here.

UI proof requires the currently open order/warehouse; facts remain durable across API restart within the running fixture, while tmpfs is intentionally destroyed afterward.
